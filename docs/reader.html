H5 商城接口回归与缺陷单 · 技术文档

v1.0 · 2026-11-17 · pytest 9 / requests 2 / allure-pytest 2 / Django 5.2
35 条接口用例 · 6 条规范化缺陷单 · 一轮回归约 8~15 秒

0. 一分钟先读懂骨架

前三个项目我们都在写功能：商城能下单、通知能消费、文件能秒传。这个项目换了个角色——写一个专门挑刺的自动检查员。

用一句话说完整件事：

先准备一个小型 H5 商城接口当「靶子」（故意留 6 个 bug），再用 pytest 按 35 条清单逐条调用接口、比对返回结果，把不对的地方自动整理成 6 张缺陷单，最后出一份能双击打开的测试报告；把 6 个 bug 修掉后，同一套清单一跑就全绿。

由外向内分三层，先记住这张图，后面每节都是往里拆一层：

层次谁在干活白话比喻主要文件
第一层 · 看板浏览器页面 + Django 视图仪表盘，按钮一按就开始考试templates/console.html、static/app.js、mall/views.py
第二层 · 检查员pytest + requests + Allure监考、阅卷、留证据、写成绩单tests/、run_regression.py、reports/
第三层 · 靶子内置 H5 商城 JSON 接口被考的学生，身上有 6 个已知错题mall/service.py、mall/urls.py、mall/models.py

一个很容易搞混的点：这次「失败」是产出，不是事故。6 条用例变红，正说明检查员把 6 个缺陷抓出来了；如果全绿反而说明靶子没犯错、没东西可报。

3. 从外向内：一次回归的完整往返

点一下看板上的「一键跑回归」，背后是这样一圈：

  1. 浏览器 POST /api/run/（Django 视图 api_run）。
  2. 视图起一个后台线程，避免把网页请求卡住；同时把 runtime/run_status.json 标成 running=true。
  3. 线程执行 python run_regression.py --reuse-server。
  4. 脚本调用 pytest，pytest 通过 conftest.py 的 session 夹具探活：MALL_BASE_URL（默认 127.0.0.1:8002）能连通就复用，没有就临时拉起一个服务，跑完关掉。
  5. 每条用例前，autouse 夹具调 POST /api/admin/reset/ 把商城恢复成干净种子数据——用例之间不许互相污染。
  6. ApiClient 用 requests 发请求，自动带 token，并记录每一次请求与响应。
  7. 断言通过/失败；失败时 hook 把证据挂成 Allure 附件，并写进 results.json。
  8. 35 条跑完，run_regression.py 汇总成 last_run.json，再生成 report.html 与 defects.md。
  9. 看板前端每 2 秒轮询 /api/state/，读到 running=false 就刷新统计卡、用例清单和缺陷单。

这圈里最值得记住的是 第 5 步和第 8 步：前者保证结果可复现，后者保证结果可交付。

4. 三层架构各自负责什么

层输入输出关键约束
看板层用户点击 / 轮询统计、清单、开关、报告链接只读运行期 JSON，不参与测试判断
测试层用例清单 + 靶子地址每条用例的通过/失败 + 证据用例只描述「正确行为」，不看缺陷开关
靶子层HTTP 请求统一 JSON 响应6 个开关决定「犯错」还是「正确」

这个分层有一个刻意的设计：用例永远写「应该怎样」，开关只改变靶子行为。所以同一套 35 条用例，开关打开时 29 通过 / 6 失败，关掉后 35 通过 / 0 失败，用例本身一个字都不用改。这就是回归测试的价值——用不变的清单反复验证修改。

6. 统一响应契约

所有接口，不管成功失败，都返回同一个外壳：

{ "code": 0, "message": "ok", "data": { "...": "..." } }

失败时 code 等于 HTTP 状态码、data 为 null：

{ "code": 401, "message": "账号或密码错误", "data": null }

test_unified_response_contract 一次检查 4 类响应（成功、参数错误、鉴权失败、业务成功），逐条确认三个字段齐全、code 与 HTTP 状态自洽。这类用例不测业务，测的是所有接口都守规矩，是接口回归里性价比最高的一类。

7. 6 个可开关的缺陷位

开关状态写在 runtime/bug_flags.json，Django 每次请求重新读，改完立刻生效。看板上可以直接逐个拨，也可以一键全开 / 全关。

编号开关缺陷级别抓它的用例
DEF-001AUTH_BYPASS_WRONG_PASSWORD错误密码仍签发 tokenP0test_login_wrong_password_rejected
DEF-002PAGE_OUT_OF_RANGE_500页码越界返回 500P1test_product_list_page_out_of_range_empty
DEF-003SEARCH_INCLUDE_OFF_SHELF搜索混入已下架商品P1test_search_excludes_off_shelf
DEF-004CART_DUPLICATE_ROW重复添加生成重复行P1test_cart_add_same_item_accumulates
DEF-005ORDER_IGNORE_STOCK不校验库存造成超卖P0test_order_reject_when_stock_insufficient
DEF-006PAY_NOT_IDEMPOTENT重复支付不拦截P0test_pay_duplicate_rejected

为什么不真的把代码写坏？因为真实项目里缺陷是「开发改出来的」，测试人员不会去改生产代码。用开关模拟，可以在同一个仓库里反复演示「发现 → 提单 → 修复 → 回归」，也不会把仓库弄脏。

9. fixture：登录态与数据隔离

tests/conftest.py 里四个夹具把重复劳动收在一处：

@pytest.fixture(autouse=True)
def fresh_state(server):
    requests.post(server + "/api/admin/reset/", timeout=10)
    yield

@pytest.fixture
def logged_in(api):
    resp, body = api.login("alice", "123456")
    assert resp.status_code == 200
    return api
  • server：session 级，一轮只做一次，负责探活或临时起服务。
  • fresh_state：autouse=True 表示每条用例自动执行，不用在用例里写。
  • api：一个干净的请求客户端。
  • logged_in / bob_client：已登录的客户端，后者用来测越权。

用例里因此看不到一句登录代码，只写断言。这就是 fixture 的意义：把「准备」和「判断」分开。

另一个细节：用例不硬编码商品主键。reset_demo() 每次重建种子数据，SQLite 自增 id 会变，所以 ApiClient.product_by_name("考研数学真题") 先按名字查回 id 再用。硬编码 id 是接口测试里非常常见的脆点。

10. 请求证据与 Allure 附件

ApiClient 每次请求都记一条：

self.calls.append({
    "method": method, "url": url,
    "request": {"json": json_body, "params": params, "token": ...},
    "response": {"status_code": resp.status_code, "body": body},
    "duration_ms": duration,
})

conftest.py 的 pytest_runtest_makereport 钩子在每条用例跑完后做两件事：把最近 10 次请求响应挂成 Allure 的 JSON 附件；把用例的模块、耗时、状态、缺陷编号、失败信息、最后两次请求写成结构化结果。

于是缺陷单里的「证据」不是手写的描述，而是真的从这一轮请求里截下来的响应。例如 DEF-006 的证据就是第二次支付返回 paid_count: 2 的那段 JSON。

13. 回归闭环：从 6 个红到全绿

同一套 35 条用例，两种状态：

14. 几个关键实现细节

  • 条件更新防超卖：正确实现用 Product.objects.filter(pk=..., stock__gte=qty).update(stock=F("stock") - qty)，受影响行数为 0 就说明库存不足，直接 409。这是数据库层面的原子判断，比「先查再改」安全。
  • 购物车幂等：正确实现按 (user, product) 查已有行，用 F("qty") + n 原子累加；缺陷态每次直接 create 新行。
  • 支付状态机：正确实现先判断 status == created 才允许支付，否则 409；paid_count 恒为 1。缺陷态不管状态一律 +1。
  • URL 顺序：api/products/search/ 必须排在 api/products/<int:pk>/ 前面，否则 search 会被当成主键匹配失败——这个坑在项目 1 的路由里也踩过一次。
  • 鉴权：API 用自定义 token（X-Token 或 Authorization: Bearer），因此中间件刻意精简，不引入 session / CSRF；看板自身的 POST 也无需 CSRF token。
  • 调用留痕：ApiLogMiddleware 记录每个 /api/ 请求的状态码与耗时，但跳过 /api/state/、/api/run/ 等看板自身接口，避免流水被轮询刷屏。
  • 后台线程跑回归：api_run 用 threading.Thread + subprocess.run 执行，状态写文件，前端轮询。这样网页不会卡 15 秒，也不会因为 HTTP 超时中断测试。

15. 踩坑复盘（这一轮真实遇到的）

#现象根因处理
1首轮 35 条里 22 条失败，大量 404，但手动 curl 全部 200环境有全局 HTTP_PROXY，Python requests 默认走代理，把 127.0.0.1 请求转发出去，拿到的是代理返回的错误页ApiClient.session.trust_env = False，同时给子进程设 NO_PROXY；curl 验证时统一加 --noproxy '*'
2一键脚本清理旧结果目录的操作被拦下涉及删除文件不做任何删除，改为每轮写独立批次目录 reports/allure-results/<时间戳>/
3本机没有 Java / allure 命令行官方 Allure 报告依赖 Java保留 allure-results，另写纯标准库 build_report.py 出免安装单页报告
4用例里写死 product_id=1 会失效每条用例前重置数据，SQLite 自增主键会变按名称查 id（product_by_name），不硬编码主键
5用例耗时显示 0.00s单条用例通常几十毫秒看板与报告统一改成毫秒显示
6看板按钮触发的回归若失败，页面可能一直转圈子进程异常时没有收尾_run_worker 用 try/except 保证任何情况都把 running 置回 false
7暗色主题下灰色标签浅字看不清主题变量没覆盖到 .pill.muted和前三个项目一样补暗色覆盖规则，并做 500px 手机端截图复核

第 1 条最值得记：测试环境问题经常被误判成业务缺陷。先把「请求到底发给了谁」确认清楚，再去看断言。

16. 自己复现与扩展

加一条新用例的顺序：在对应模块写 def test_xxx(...) → 用 @pytest.mark.defect("DEF-00X") 标注是否对应缺陷 → 用 logged_in / api 夹具 → 写断言 → 重跑 run_regression.py，看板和报告会自动把新用例纳入统计（数字从 35 变 36 不需要改任何前端代码）。

要接真实服务：设置 MALL_BASE_URL=http://<host>:<port>，只要对方遵守 {code, message, data} 契约，用例可直接复用。

17. 术语速查与简历可写要点

术语速查：SUT 是被测系统、fixture 是夹具、hook 是钩子、assertion 是断言、regression 是回归、idempotency 是幂等、contract 是契约、severity 是严重级、evidence 是证据、artifact 是产物。

简历里可以据实写的几句话：

  • 基于 pytest + requests 设计 35 条 H5 商城接口回归用例，覆盖认证、商品、搜索、购物车、订单、支付、契约与性能 7 个模块。
  • 通过 fixture 统一管理登录态与数据隔离，通过 pytest hook 自动收集请求/响应证据并生成 Allure 附件。
  • 产出 6 条规范化缺陷单（含复现步骤、预期/实际、根因与修复建议），并用缺陷开关演示「发现 → 修复 → 回归」闭环，修复后用例通过率从 82.9% 升至 100%。
  • 输出 JUnit XML、Allure 原始结果、免 Java 单页报告与可视化看板，支持一键回归。

文档随代码存于 docs/，docs/reader.html 为离线双 Tab 阅读版，双击即可打开。

这次我不写功能了，我写了一个专门挑刺的机器人

项目 4 手记 · 2026-11-17 · pytest / requests / Allure / Django

前三个项目，我一直在做「加法」：给二手交易平台加下单、给订单通知加幂等、给大文件上传加秒传。每次交付的时候，我都会顺手点一遍页面，确认功能没坏。

但这个「顺手点一遍」一直让我有点心虚。功能是我自己写的，测试也是我自己点的，等于自己给自己批卷子。于是第四个项目我换了个方向：不写业务功能，专门写一个自动检查员，让它按清单去调接口，把不对的地方一条条记下来。

做完之后我最想说的不是「35 条用例」，而是这个体会：测试里变红的那些用例，不是失败，是产出。

一、先得有个「被考的人」

写接口测试第一个尴尬问题是：测谁？

两周计划里写的是「基于 H5 商城」，也就是项目 1。但我回去翻了项目 1 的代码，发现它是典型的页面型站点：表单提交、模板渲染、跳转重定向，并没有返回 JSON 的 REST API。硬把它改成接口服务，动静太大，而且会把前面已经稳下来的项目再搅一遍。

所以我做了个折中：在测试仓库里内置一个轻量靶子。业务契约和项目 1 完全一致——用户、商品、搜索、购物车、订单、支付，但用纯 JSON 接口暴露出来。这样任何人 clone 这个仓库，不用先启动三个别的项目，一条命令就能把整套回归跑起来。

回头看，这个决定反而让项目更干净了：被测系统和测试套件放在一个仓库里，版本是对齐的。以后项目 1 真加上 API，只要把 MALL_BASE_URL 指过去，用例在契约一致的前提下不用改。

靶子里我埋了 6 个开关，对应 6 个真实感很强的缺陷：错误密码能登录、分页越界 500、搜索混入下架商品、购物车重复添加不累加、下单不校验库存、重复支付不拦截。开关打开，靶子故意犯错；开关关掉，相当于开发把 bug 修完了。

二、那一晚上的 22 个假失败

第一次跑一键回归，终端刷出来 22 条失败。

我预期的是 6 条。多出来的 16 条几乎全是 404，而且特别诡异：/api/health/ 是 200，/api/products/ 有时 200 有时 404；同一个 /api/auth/profile/，不带 token 的请求正常返回 401，带上 token 反而 404。

我第一反应是路由写错了，去翻 urls.py，翻了三遍，没问题。又怀疑是 fixture 重置数据把服务搞坏了，也不对——404 是路由层面的事，跟数据无关。

真正的转折是我去看服务日志：pytest 期间的请求，一条都没进到被测服务的日志里。

那它们去哪了？打印一下环境变量：

HTTP_PROXY=http://127.0.0.1:54397

这台机器上有全局代理。Python 的 requests 默认会读环境里的代理配置，把 127.0.0.1 的请求也转发出去；而 curl 直连本地，所以我手动验证时一切正常，一到 pytest 就全乱。代理返回的错误页恰好是个 Django 风格的 404 页面，把我骗了小半个晚上。

修法只有一行，但很关键：

self.session.trust_env = False

让测试客户端不走环境代理，直连本机。再跑，35 条用例变成 29 通过 / 6 失败，6 条红正好对应 6 张缺陷单，一个不多一个不少。

这件事给我留下的经验比任何一条用例都深：测试环境的问题，经常被误判成业务缺陷。断言失败时，先确认「这个请求到底发给了谁」，再去看业务逻辑。后来我把这条写进了技术文档的踩坑复盘第一条。

三、把「挑刺」变成可交付的东西

检查员不能只会在终端里刷 FAILED。真正能被别人用的，是这四样东西：

  • JUnit XML：CI 流水线都认的通用格式；
  • Allure 原始结果：有 Java 的机器上 allure serve 就能出官方报告；
  • 免 Java 单页报告：本机没有 Java，我用纯标准库渲染了一份 report.html，统计条、分组用例、失败断言、请求响应证据、缺陷单全在里面，双击即开；
  • 6 条规范化缺陷单：编号、严重级、接口、前置条件、复现步骤、预期结果、实际结果、证据、根因推测、修复建议、关联用例。

为了让「证据」不是我手写的一段描述，我在 pytest 的 pytest_runtest_makereport 钩子里做了一件事：每条用例跑完，把最近 10 次请求和响应以 JSON 附件的形式挂上去。所以 DEF-006 缺陷单里写的「第二次支付返回 paid_count: 2」，是那一轮真真切切截下来的响应体。

还有一个小设计我很喜欢：缺陷数据只定义一次（defect_catalog.py），看板、单页报告、Markdown 缺陷单三处都从它读。不会出现报告里写 P1、看板上写 P2 这种低级不一致。

四、最爽的一刻：从 6 个红到全绿

看板上有个按钮叫「模拟开发修完全部缺陷」。点下去，6 个开关全关；再点「一键跑回归」，同一套 35 条用例，一个字都没改：

缺陷开关通过失败通过率
修复前6 / 629682.9%
修复后0 / 6350100%

我盯着那个 100% 看了几秒。前三个项目交付时，我的满足感来自「页面能用了」；这次的满足感来自「我能证明它没问题了」。这两件事其实很不一样。

以前我以为回归测试就是「改完再跑一遍」，现在更愿意这样理解它：用一份不变的清单，反复证明这次修改没有把别的地方弄坏。清单越稳定，这句话越有分量。

五、一个和代码无关的小插曲

一键脚本原本有一句「跑之前清空上一轮 Allure 结果目录」。执行的时候，这一步被环境拦下来了——它涉及删除文件。

我当时的选择是：不较劲，也不换个别的方式偷偷删掉，直接改设计。每轮结果写进带时间戳的批次子目录，旧的原样留着，新的单独放。改完反而更好：既能对比不同批次，也不会误删任何东西。

后来越想越觉得这个改动挺有意思。做测试的人天天在讲「不要破坏现场」，结果自己的脚本第一个想干的事就是清现场。留痕比干净更重要。

六、我实际学到了什么

不列知识点，说三个真的进到脑子里的东西：

  1. 夹具（fixture）是「把准备和判断分开」。我把重置数据、起服务、登录拿 token 全放进 conftest.py，35 条用例里看不到一句登录代码，只写断言。读用例的时候，一眼就知道它在检查什么。
  2. 断言要写「应该怎样」，不能写「现在怎样」。我一开始差点让用例去读缺陷开关、根据开关决定期望值，那样就等于让考卷跟着学生答案改。开关只改靶子，用例永远写正确行为，回归才有意义。
  3. 用例不硬编码主键。每条用例前重置种子数据，SQLite 自增 id 会变，所以改成按商品名查 id。这类「脆点」不痛一次是记不住的。

另外还有个很实际的收获：我现在能说清 pytest / fixture / hook / Allure / JUnit XML / 契约 / 幂等 / 严重级这些词分别是干什么的，而不是只在简历上见过它们。

七、下一步

四个项目连起来，简历上的形状开始清楚了：一个完整的业务系统，两个后端硬核点（幂等消费、分片上传），再加一个测试方向的收口。剩下的项目里还有 Java 方向和文档方向，不急，一个一个来。

如果你也想照着做一遍，最省事的路径是：先点一遍看板的「一键跑回归」，对着「事件流水」倒推每一步；再打开 report.html 看 6 张缺陷卡；最后把 6 个开关关掉重跑一次，看它全绿。代码可以先不读，流程走通了再回头看 tests/ 目录，会觉得顺很多。
